# ddo-data

Rust workspace that turns Maetrim's DDOBuilderV2 data files into SQLite and serves it as a read-only HTTP API. This file is the instruction set for every coding agent working here (Claude Code, Codex, and others that read `AGENTS.md`); `CLAUDE.md` is a symlink to it.

## Quick Reference

```bash
export PATH="/opt/homebrew/opt/rustup/bin:$PATH"   # cargo is keg-only on the maintainer's Mac
cargo test --workspace
cargo lint                          # clippy -D warnings, the data-file checks (schemas, templates, column coverage, citation fields, retired inputs), the API contract and scale guards (list-parameter docs, pack query count), then the no-comments check; what CI runs
cargo fmt --all --check
cargo xtask no-comments --fix       # strip every comment and doc comment
cargo xtask refresh-examples        # rebuild crates/ddo-api/docs/examples/v1 from a build of data/ (or --db PATH)
cargo run --release -p ddo-etl -- import-ddobuilder --previous DIR --source DIR --data data   # merge Maetrim's new DataFiles into the data files (docs/update-from-maetrim.md); the only command that reads his XML
cargo xtask check-db ddo.db         # run the integrity checks on a built database; fails on any HARD check
cargo xtask validate-api --db ddo.db --all-details  # validate every served response against its schema (the deploy runs it)
cargo xtask wiki-tooltips --db ddo.db               # compare served lines with the wiki golden set in xtask/data/tooltip_golden.json; fails on an unrecorded mismatch (the deploy runs it and fails on a mismatch; an upstream text change arrives through import-ddobuilder, where it is reviewed first)
cargo xtask check-redirects --db ddo.db --deployed deployed.sqlite   # fail on a redirect row older than 30 days, and (with --deployed, a downloaded live /v1/dump.sqlite) on a served slug the build lacks without a row in data/redirects.toml; the deploy runs it
cargo run -p ddo-etl -- prune-redirects --data data   # delete redirect rows older than 30 days
cargo run -p ddo-etl -- build --data data --out ddo.db   # the database from the data files; the only build there is
DDO_DB_PATH=ddo.db ICONS_DIR=icons cargo run -p ddo-api
```

## Orientation

This is the data half of a two-repo project. The site is `ddo-tools`, a sibling directory under `~/Documents/Personal Projects/` (GitHub `WestonChan/ddo-tools`, live at https://ddo-tools.com, its own `AGENTS.md`). This API is live at https://ddo-data.fly.dev (Fly app `ddo-data`, region `ord`, suspends to zero between requests; `/v1/docs` is the OpenAPI UI and `/docs` redirects to the latest version, `/v1/version` reports the dataset SHA and row counts).

**Data flow.** `data/` (the TOML data files, one per entity) → `ddo-etl build --data data` → `ddo.db` (~14 MB SQLite, schema from `ddo-model`) → `ddo-api` serves it read-only with strong ETags → `ddo-tools` reads it over HTTP through `src/lib/api/`. Maetrim's DDOBuilderV2 `Output/DataFiles` enters only through `ddo-etl import-ddobuilder` (`docs/update-from-maetrim.md`), which merges his changes into the data files. Every response is immutable for a deployment. Successful responses are cacheable for five minutes (`public, max-age=300, stale-while-revalidate=3600`, the same for `/v1/dump.sqlite` and `/icons/`, whose URLs carry no version) and then revalidate against the ETag, which hashes the dataset SHA, the API commit, the path and the query, so a deploy is visible within minutes; `/v1/version` is `no-cache` (always revalidated) and every 4xx and 5xx is `no-store`, all set in `crates/ddo-api/src/cache_policy.rs`.

**Deploying.** Only through `.github/workflows/deploy.yml` (every push to `main` except Markdown-only ones, or `workflow_dispatch` with `force`): it reads the dataset commit from `data/upstream/commit.toml`, skips if the live `/v1/version` already reports both this commit (`api_commit`, baked in at build time from `DDO_API_COMMIT`) and that dataset commit, builds `ddo.db` and the icons from `data/`, checks row-count floors, runs `check-db` (a HARD failure stops the deploy), `validate-api` and `wiki-tooltips`, downloads the live `/v1/dump.sqlite` and runs `check-redirects` against it (a served slug missing without a row in `data/redirects.toml` stops the deploy), and runs `flyctl deploy --remote-only` with the `FLY_API_TOKEN` secret. Nothing in the deploy or CI reads Maetrim's repository. The `Dockerfile` copies prebuilt artifacts, so `fly deploy` from a laptop does not work; `fly status -a ddo-data` is fine for inspection.

**Local API for the frontend.** `DDO_DB_PATH=ddo.db ICONS_DIR=icons PORT=8089 cargo run --release -p ddo-api`, then `VITE_API_URL=http://localhost:8089` in `ddo-tools/.env`. Icons come from `cargo run -p ddo-etl -- icons --out icons`.

**The data files (V9).** The dataset is TOML under `data/` at the repository root, one file per entity, and it is the only input to the database build. The root is `packs/`, `characters/`, `effects/`, `upstream/`, `redirects.toml` (dated slug redirects and retirements, 30 days each), `icons/`, the generated `.schemas/` and `.templates/`, and `README.md`, and `data/README.md` opens with the rule that places everything: a source holds what it yields, at the narrowest folder its sources resolve to. A pack folder is tagged with the update it shipped in (`packs/u037-mists-of-ravenloft/`, modules `m3-`, the two beta packs `m0-`), derived from the cited `update` on its `pack.toml`. Inside a pack, quests, crafting systems, vendors and events are folders holding their record (`quest.toml`, `crafting.toml`, `vendor.toml`, `event.toml`) and a `gear/` folder with what they yield (crafting systems also `augments/`); chains, sagas, sets, patrons, filigree sets and challenges are files in their kind folders; the pack's own `gear/` holds pack-wide drops, chain, saga and challenge rewards, and gear that drops from several quests; `augments/` what the pack yields outside one system. One gear file lives under the one quest that drops it, else the pack's `gear/` when several do, else the one vendor, crafting system or event that yields it. The pseudo-packs `free-to-play/` (by patron), `shared/` (what spans packs, at its narrowest level; `shared/augments/<family>/` for the 810 augments with no single system), `general/` (starter gear, the store, world drops) and `unsourced/` (gear with no known source) carry no tag and take the same shape. `characters/` holds classes, races, feats, spells, enhancement trees (`enhancements/<tree>/tree.toml` with its own `icons/`), stances and buffs; `effects/` holds the named effects directly, with `stats/`, `stat-groups/`, `tiers/`, `clickies.toml` and the vocabularies beneath; `upstream/` the commit the files were exported from, the excluded items and the source aliases; shared art is `icons/<kind>/`. The files hold what a person writes, and nothing derived:
- `[[source]]` rows as the API serves them, effects and sockets.
- Booleans are omitted when false.
- `is_wiki_only = true` marks an item, augment or quest that only the wiki knows. Quest chains, sagas, vendors, events and crafting systems are wiki entities by kind.
- `[[ddobuilder_correction]]`s mark where our value differs from Maetrim's, with `upstream` his value.
  - A merge of several of his spellings into one name is one correction whose `upstream` lists them all.
  - Two separate corrections with one target fail on every kind.
- `[[citation]]`s record a check: one citation on the whole entity by default, with `field` (a field or nested array of the record it sits on) only for a partial check.
  - Each correction and each citation has exactly one source: `url` or `in_game = true`, with `read` the date. An optional free-text `note` goes with it.
  - A citation means only "checked". No code reads its `field` (`CitationField` in Rust, and `deny_citation_field_reads` for SQL).

The database holds every value in typed columns and rows. File names are slugs (the name plus `variant`); references are display names; `cargo run -p ddo-etl -- find "<text>"` prints every entity whose name or slug contains the text with its path, or the nearest names, reading the files directly; an unresolved reference fails the build with every other one at once, each naming the file, the array and index, the kind, the name, the path the rule expected and the nearest existing names. `cargo run -p ddo-etl -- build --data data --out ddo.db` builds from it and `ddo-etl export --db ddo.db --out DIR` writes it back; `cargo xtask round-trip --data data` proves both directions (byte-equal files, equal tables and responses), and CI runs it. `cargo xtask diff-db --by-slug A.db B.db` compares two builds table by table and response by response. Ids are hashed from kind and slug at build and never written. Nested rows have no id. A file whose folder no longer matches what its sources imply gets a WARN naming the move, and the next export moves it. `data/README.md` and `docs/data-icons.md` describe editing: a file for a correction to something that exists; the database and `export --db` for anything that touches many entities, such as a new pack or Maetrim's update.

Every kind of file is declared once (`declare_file_kinds!` in `tree/schemas.rs`), with one of four placements:
- `Entity`: a path built from the slug.
- `Rows`: a single vocabulary file.
- `GroupedRows`: one file per group, such as `characters/feats/{group}.toml`.
- `Dataset`: the four bookkeeping files (`upstream/commit.toml`, the excluded items, the source aliases and the pack exceptions). These have no template.

From that one declaration come its schema in `data/.schemas/` (`taplo.toml` maps them for editors) and a copyable template in `data/.templates/`, both written by export. `cargo lint` checks:
- every file against its schema
- that every template builds
- that every database column is declared by a record or listed in `UNPOPULATED_COLUMNS` (verified NULL; V11 fills the four listed)
- that each file is named for its slug
- that every reference resolves Two kinds of change: a fact about one entity (a value, a correction, a citation, a source) is a hand edit to its file, validated by `ddo-etl build --data data`; a change across many entities (a new pack, a rename everywhere, Maetrim's update) is made in a built database and written back with `ddo-etl export --db`, so the export does the placing; `data/README.md` has both sequences, and `ddo-etl import-ddobuilder` (`docs/update-from-maetrim.md`) is the second one automated for his pushes.

**Where upstream is.** Only `ddo-etl import-ddobuilder` reads Maetrim's XML, through its `--previous` and `--source` directories. `build`, `icons`, `export`, `refresh-examples`, `check-db`, the deploy and CI all read `data/`. `upstream/` is a gitignored checkout of his repository, kept for preparing an import (see `docs/update-from-maetrim.md`). A `git worktree` of this repo has none, so point the import at a checkout of each commit, for example `~/.cache/ddo-data/upstream-<sha>/Output/DataFiles`.

**Where the API surface is.** `crates/ddo-api/src/routes/` has one file per resource (`items` with its slot, weapon, damage and socket vocabularies, `augments`, `sets` with filigrees and sentient gems, `feats`, `stances` for the standalone stance list, `buffs` for guild and optional buffs, `races`, `classes`, `enhancement_trees`, `spells`, `bonuses` for bonus types and the effects vocabulary (`/v1/effects`, stats and named effects with `kind`; `/v1/effects/{slug}` for either), `quests` for quests, challenges, packs and patrons, `quest_series` for quest chains and sagas, `vendors_and_events` for the wiki vendors and events, `crafting` for the wiki crafting systems, `dump`, `version`); Every detail route is `/v1/<kind>/{slug}`, resolved by `entity_slugs.rs` through the one `EntityKind` declaration in `crates/ddo-model/src/enums.rs` (current slug, then a redirect's 308, then, until ids leave the API, a numeric id); every served `*_id` has a `*_slug` beside it, checked by `reference_slugs.rs`. `db.rs` holds the shared query helpers; `etag.rs` and `cache_policy.rs` the caching headers and `state.rs` the pool. The ETL mirrors it: `crates/ddo-etl/src/xml/` parses, `map/` applies `data/*.toml` vocabularies, `build/` writes tables.

**Planning.** The roadmap for both repos is `ddo-tools/docs/roadmap.md` (V-series section).

## Structure

- `crates/ddo-model` — the schema as Rust: enums, seeds, DDL, `SCHEMA_VERSION`. Based on ddo-tools' schema, not on DDOBuilderV2's XML; the ETL is the adapter.
- `crates/ddo-etl` — parses `Output/DataFiles` with quick-xml and writes SQLite: items, augments, sets and filigrees, sentient gems, feats, stances, races, classes, enhancement trees, spells, clickies, guild and optional buffs, quests, challenges and patrons. Only `AttackRates.xml`, `BonusTypes.xml`, `IgnoredList.xml` and `WeaponGroupings.xml` are unread. Mapping vocabularies are data in `data/*.toml`, listed in `crates/ddo-etl/data/README.md` with the items the build leaves out or flags legacy; an unmapped value fails the build on purpose. A stat is what a number lands on, a bonus is a typed amount to a stat, and an effect is the named line that grants bonuses plus its prose, as the game words them. `effects` holds both stats (`is_stat`, `category`; seed ids kept) and named effects in one table, so every name has one meaning: a stat row is also the plain line for that stat ("Constitution"), a named effect ("Firestorm Lore", "Hallowed", "Riposte") grants bonuses through `effect_bonuses` (stat, bonus type where the definition fixes it, `amount_from` 1 or 2 reading a link value or 0 a `constant`, `scale` and `rounding`, a nullable `trigger_id`). Each effect carries its display-text title as name, a `verbose_name_template` (the full line as DDO writes it) and a description template (their placeholders are the amount count), a home bonus type that its lines leave unsaid, defaults, and an optional tier group (`effect_tier_groups`: Deception, Improved Deception). The owner links (`item_effects`, `augment_effects`, `set_bonus_tier_effects`, `feat_effects`, `item_augment_slot_option_effects`) carry `value`, `value2`, `bonus_type_id` and the order; a link to a stat row is that stat at the link's value and type, with no bonus row, so the writer copies a fixed type onto it and the build fails on a stat link with no type. The view `owner_bonuses` is the single read path for what an owner grants (stat, type, amount, `via_effect_id`, `amount_source` of `owner`, `default` or `constant`, `scale`); the API and the stats engine read it. `effect_damage` (dice, damage type, `triggers` row, value scaling) takes damage lines as they are found; the raw dice in `modifiers` are the backfill list. One cached writer (`EffectCache` in `build/effects.rs`) writes all of it; `effect_map.toml` is the single vocabulary (buff and effect types, qualifiers, companion words, energy artifacts, tier groups, names). The resolution rules are in `crates/ddo-etl/data/README.md`; the check-db WARN lists (`effect_types_not_classified`, `effects_named_like_identifiers`, `effects_text_only_with_item_values`, `effect_links_missing_first_amount`, `effects_with_dice_but_no_damage_rows`, `effects_with_tied_home_bonus_types`, `effect_templates_disagree_with_names`, `owner_bonuses_repeated_across_links` (a link whose resolved stats and types another link of the same owner already covers), `effect_descriptions_with_fewer_critical_dice_than_hit_dice`) are the standing work lists; `owner_stat_links_repeat_effect_links` (a direct stat link beside an effect link granting the same stat, type and amount) is HARD.
- `crates/ddo-api` — axum read API over the ETL output. OpenAPI at `/v1/docs`, strong ETags, `X-Dataset-Version`, rate limiting, `/v1/dump.sqlite`, icons at `/icons/`.
- `xtask` — repo tooling behind `cargo xtask`. Not published.
- `upstream/` — gitignored sparse checkout of DDOBuilderV2, used to prepare the import's `--previous`/`--source` directories. The deploy never reads it.
- Planning lives in the ddo-tools roadmap (`docs/roadmap.md`, V-series section), not here.

**Wiki facts and corrections.** Everything read from ddowiki lives in the data files beside his values. That covers:
- which quest drops are rare
- each quest's free-to-play status, legendary level, zone, quest giver and flagging
- crafting systems with their ingredients and recipes
- quest chains and sagas with their quests and end rewards
- vendors and events with their offers
- descriptions his files leave blank
- the items, quests and augments only the wiki knows (`is_wiki_only`)

The rules his values follow:
- **His files win for every value they carry.** A wiki fact only adds.
- **A value of his that the wiki contradicts is a `[[ddobuilder_correction]]`.** It cites the page and carries his value as `upstream`.
- **His blank never erases ours.**
- **The five quest columns only the wiki supplies are always ours.** These are `OURS_ONLY_COLUMNS` in `delta/table_merges.rs`.

`provenance` and the annotation tables (`citations`, `corrections`, `removed_entities`) are internal. The API never returns them; `/v1/version` counts the wiki rows as `wiki_items`, `wiki_quests` and `wiki_augments`.

**The import's two builds of his XML.** `ddo-etl import-ddobuilder` builds A (his previous XML) and B (his new XML) through the XML mapping in `crates/ddo-etl/src/build/`. The wiki facts come from the data files (`WikiOverrides::from_database`) and so do the corrections (`Corrections::from_database`), so a wiki row is identical in A and B and never part of his delta. The fill step (`import_ddobuilder/blanks.rs`) then:
- fills every blank cell of a row both sides hold from ours, reporting `BLANKED UPSTREAM, OURS KEPT` where he blanked a value he had
- sets the ours-only columns unconditionally

Wiki facts behave differently in each build:
- **In A,** a wiki fact naming something only his later files have is left out and reported as `SKIPPED WIKI FACT`.
- **In B,** such a fact fails the import, naming its data file.

The 12 SunAndMoon gems whose description he leaves as "Drops in: ?" carry a description correction. His edit to one of those descriptions is reported as the stale-correction CONFLICT, for a person to settle. The XML-only mapping audits print as import report lines. The roadmap's V9 entry records the XML-path inputs this replaced and why they went; the `retired_inputs` guard keeps them gone.

## Worktrees

Any change goes in a git worktree, never in a checkout someone else may be using:

```bash
git worktree add -b <branch> /tmp/ddo-data-<branch> main
```

The worktree compiles from scratch into its own `target/` (a few minutes the first time). When done: commit on the branch, fast-forward `main` from the main checkout, push, `git worktree remove` the directory and delete the branch. Never run a bare `git stash`; the stash is shared across worktrees.

## Code Quality

- **No comments, no doc comments.** Code carries its meaning in names, types, and tests. Do not write `//`, `/* */`, `///`, or `//!`. If something needs a comment to be understood, rename, split, or restructure it until it doesn't. Reasoning that cannot live in code goes in the ddo-tools roadmap or `docs/` there. `cargo lint` fails on any comment; `cargo xtask no-comments --fix` strips them.
- **Turn findings into lint rules.** When you fix or review a problem a machine could have caught (a convention broken in more than one place, a bug pattern, a rule in this file that nothing enforces), suggest a check that `cargo lint` runs so it can't come back: a clippy lint in `[workspace.lints]` or `clippy.toml`, or an `xtask` check. Say what it would flag today and include it in your final report. Add it yourself when it's cheap and needs no new dependency; a new crate needs the maintainer's approval first.
- **Names carry the meaning comments would have.** Follow the naming rules below.
- **Keep code clean and refactor freely.** Improve adjacent code you touch; don't leave a file worse than you found it.
- **`cargo lint` also enforces** `unreachable_pub` (so a crate-internal item is `pub(crate)` and dead code stays visible) and the naming lints in `[workspace.lints]` and `clippy.toml`: `disallowed_names` (`data`, `info`, `tmp`, `val` and similar), `many_single_char_names` (three or more single-letter bindings in one scope) and `similar_names`. Every crate opts in with `[lints] workspace = true`.
- `rustfmt.toml` sets a 120-column width. Run `cargo fmt --all` before committing.

### Naming

Names replace comments, so each name must answer the question a reader would otherwise ask. **Before naming or renaming anything, read `ddo-tools/docs/naming.md`** (the sibling checkout, or [on GitHub](https://github.com/WestonChan/ddo-tools/blob/main/docs/naming.md)). It covers how to choose a name, with examples and sources, and applies to both repos. Its examples use TypeScript casing; here the same words go in `snake_case` and `UpperCamelCase`. Existing code predates it and is not a model to copy; rename what you touch. The rules in short:

- **Choose, don't guess.** List the concepts the name must carry, pick one word per concept (the player's word, the same word the frontend and API use), put them in English order (`maximum_message_length`, `total_strength`, `cooldown_ms`), then read the call site on its own.
- **Code that changes data** is an imperative verb phrase naming what it changes, or why: `insert_quests`, `reject_unmapped_slot`. Never `update`, `process` or `handle`. A name that needs "and" means the function should be split.
- **Code that only reads, and every binding,** is a noun phrase naming what it is or what it's for, often through the process that made it: `sorted_items`, `rows_to_insert`. Reads have no side effects. Follow the Rust API Guidelines: no `get_` on getters; `as_`/`to_`/`into_` for conversions; `new`/`from_x` for constructors; `is_`/`has_`/`can_` for predicates.
- **Types are nouns**: the domain word if one exists (`Race`, `Augment`, `EquipmentSlot`), otherwise the role the thing plays. No `Manager`, `Helper`, `Info` or `Data`. Enum variants read as values (`Difficulty::Elite`).
- **A name means only one thing.** Qualify generic words (`slot`, `candidate`, `entry`, `child`, `kind`) until only one reading is left. Add words that remove ambiguity and drop words that repeat the type or the owner.
- **Name length follows scope**: short names only for values that live 10 lines or fewer. `ddo-model` and shared helpers get capability names, not a name from their first caller's point of view.

## API documentation

`/docs` is the public face of the API, and it is generated from the `#[utoipa::path]` attributes, so the attributes are the documentation. Every route carries `summary` (a short title in the form "List items" / "Get an item"), `description` (at most two sentences and 180 characters, what the route returns; the conventions it follows are written once in the Introduction, not repeated per route), a one-sentence `description` on every query and path parameter (what it matches, the vocabulary it comes from, the default), and a `description` on every response. Every response body is a typed schema from `crates/ddo-api/src/routes/v1/response_schemas.rs`, so the docs page renders field trees and the site's API types come from the same document; a field carries a description only where it adds meaning. A contract test serves every list and detail route over the fixture database and validates each response against its schema, so a handler change that drifts from its schema fails `cargo test`; when a response shape changes, change its schema in the same commit. Query parameters are declared through `declare_query_parameters!` and `declare_list_parameters!` in `crates/ddo-api/src/query.rs`, which hold each field's description beside its type, because the comment ban leaves no other place to describe a field. The `tags(...)` and `info(description)` on `ApiDoc` in `routes/v1/mod.rs` are the sidebar headings and the Introduction page. `openapi_describes_every_operation_parameter_and_tag` in `crates/ddo-api/tests/api.rs` fails the build when any of this is missing or too short, so adding a route means writing its docs in the same commit. When a response shape changes, reread its description.

**List parameters.** Every list route takes the same four parameters through `ListQuery`: `q` (a case-insensitive substring of the row's name; `items`, `augment-slot-types` and `effects` document their own meaning: on `/v1/effects` a stat-name query also returns the effects granting that stat, after the direct matches, never the other way), `limit`, `offset` and a repeatable `sort` (`sort=-name&sort=minimum_level`; a leading `-` is descending, key order is precedence, omitted keeps the route's default order), and returns `{ total, limit, offset, <rows> }`. Route-specific filters live in a sibling struct read through `ApiQuery<T>`. Each route names its sortable columns in one `*_SORT_FIELDS` constant; the `sort` description and the 400 for an unknown field are generated from it, and an unknown query key is a 400 naming every key the route accepts. Every filter and every scalar column of the row is sortable (booleans false before true, nulls last), and a contract test over all list routes derives the required set from the route's filters and row keys, so a new filter or column cannot ship unsortable. Vocabulary filters (`slot`, `category`, `pack`, `quest`, `quest_chain`, `saga`, `bonus`) take repeated keys meaning any of them; `<name>_match=all` switches to all of them where an item can carry several (`slot_match` and `category_match` are a 400). `list_parameter_docs_share_descriptions_and_match_runtime_sort_fields` and `list_endpoints_reject_unknown_query_parameters_as_json` in `crates/ddo-api/tests/api.rs` keep the docs and the runtime in step, and `cargo lint` runs the first. The conventions themselves (AND-ed filters, repeated keys never comma lists, `q`, paging, `sort`, 400 behaviour) are written once under "Query parameters" in the Introduction (`info(description)` in `routes/v1/mod.rs`); a new list route adds a `*_SORT_FIELDS` constant and a `declare_list_parameters!` call and inherits the rest.

Every JSON response also carries an example, attached after generation by `crates/ddo-api/src/docs.rs` from `crates/ddo-api/docs/examples/<route>.json`. The files are real responses, written by `cargo xtask refresh-examples`: it builds a database from `data/` or reads `--db PATH`, serves each sample request in its `EXAMPLE_REQUESTS` list (`xtask/src/response_examples.rs`, one per example file) through `ddo_api::app` in-process, trims every array to three elements, sorts keys, and keeps the `api_commit` already in `version.json`. It fails, naming the example, when a sample does not return 200 or when the list and `RESPONSE_EXAMPLES` disagree; a new route needs a sample there too. The quest chain, saga, vendor and event examples are the exception: until a wiki file records one, their routes return `[]` and 404, so the refresh keeps the committed `quest-chains*.json`, `sagas*.json`, `vendors*.json` and `events*.json` (made with `--db` from a scratch build holding draft entries; the vendor and event ones name only a page, so their items are those his drop text gives) instead of failing. `openapi_carries_a_real_example_for_every_json_response` compares each example's keys and value types against a response from the fixture database, so a shape change fails until the examples are refreshed, and a new route fails until it has one.

**Versions.** The API is versioned by path prefix and every version owns its documentation: `routes/v1/` holds the handlers, the `ApiDoc` (info, tags) and the `RESPONSE_EXAMPLES` list, its examples live under `docs/examples/v1/`, and `lib.rs` mounts its spec at `/v1/openapi.json` and its UI at `/v1/docs`. `/docs`, `/openapi.json` and `/` redirect to `routes::LATEST_VERSION`. A breaking change (renaming or removing a field, changing a shape, changing what a filter matches) goes in a new `routes/v2/` beside `v1`, not in place: copy the module, change what must change, register it in `app()` next to v1, point `LATEST_VERSION` at it, and keep v1 serving until `ddo-tools` and any other consumer have moved. Additive changes (new field, new route, new optional filter) stay in the current version. The one exception so far: Phase 4e (2026-10-04) changed v1's item, augment and set detail and replaced `/v1/enchantments` with `/v1/effects` and folded `/v1/stats` and `/v1/stats/{id}` into it in place, because the site was the only consumer and moved in the same landing; once anyone else reads the API, the v2 rule holds without exception.

## Testing

Write the failing test first, confirm it fails for the right reason, then the minimum code to pass, then the full suite. Parser tests use fixtures under `crates/ddo-etl/tests/fixtures`; API tests build an in-memory database. `cargo test --workspace`, `cargo lint`, and `cargo fmt --all --check` must all pass before committing.

**Integrity checks.** `cargo xtask check-db PATH` runs the named checks in `INTEGRITY_CHECKS` (`xtask/src/integrity.rs`) against a built database and prints `check <name>: ok`, or the offender count, the first offenders and any notes. Single-table rules are schema constraints in `ddo-model` (a non-blank item name and an existing slot, an item's ddowiki `wiki_url`, a page on every wiki row, a pack on every quest that is no challenge, no chest on a reward and no chest that says reward, a bonus row's amount source and positive `scale`, a bonus row's stat being a stat row, a link's value before value2, and foreign keys, which the build connection enforces on every insert), so the build itself fails on them and the schema tests assert each one; cross-table rules are check-db, and the effect writer fails the build on the same ones as it writes (a link's amounts against its effect's template placeholders, where a bonus type comes from, a stat link's type, tier group membership). A HARD check (legacy items, empty tables, weapon and armor stats, raid loot, socket families, unapplied corrections, trees, class progressions, quest chains and sagas without quests) fails the command; a WARN check (items without a source, effects named after stats, and the other work lists) prints its offenders and never fails. `items_without_a_source` stays WARN while sources remain unmodelled (vendors and events no wiki file records yet, the DDO Store, wilderness areas) and becomes HARD once they are read or modelled; its drop-location heads are the work list. `--allow-empty-table NAME` exempts a table from `tables_not_empty`. The deploy workflow runs it on `ddo.db` after the row-count floors and before the deploy, allowing `vendors` and `events` to be empty until the wiki files record one, so a HARD failure stops the deploy; CI builds the fixture database from `crates/ddo-etl/tests/fixtures/data` and runs it there, allowing the tables the trimmed fixture leaves empty. A rule over one row of one table belongs in the schema as a constraint, not here. To add a check, append an `IntegrityCheck::hard` or `IntegrityCheck::warn` to `INTEGRITY_CHECKS` with a description and either an SQL query returning `(name, id, detail)` per offending row or a function building the findings, and add its injected violation to `injected_violations` in `xtask/tests/integrity.rs`. A new HARD check that fails on a full upstream build lands as WARN with its description naming the follow-up, so the deploy keeps passing while the data is fixed.

## Dependencies

- `xtask` uses `ra-ap-rustc_lexer`, which asserts at compile time that `unicode-ident` and `unicode-properties` share a Unicode version. `Cargo.lock` pins `unicode-ident` to 1.0.24 until `unicode-properties` catches up; a bare `cargo update` reintroduces the mismatch. Bump both together.
- Docker is not installed on the maintainer's Mac; the image is only built by the deploy workflow.

## Commits

Plain imperative subjects, no prefixes. One logical change per commit, passing `cargo lint` and tests. Push to `main` directly; CI runs on every push, and the deploy workflow runs on every push that changes more than Markdown and on dispatch.

`.github/dependabot.yml` opens weekly PRs (Mondays, after a 7-day cooldown) for Cargo and GitHub Actions, minor and patch bumps grouped into one PR per ecosystem, majors separate, `unicode-ident` with `unicode-properties` always together (see the pin above), and `utoipa` with `utoipa-axum` and `utoipa-scalar` always together because they share one `utoipa` type. The `utoipa` and `unicode` groups come before `cargo-minor-and-patch` in the file because a dependency joins the first group it matches. Merging one deploys, so merge only once CI passes, then pull `main`.
